Architecture

Overview

Processor, Editor, sequencer engine, voices and signal flow — the map of the source tree.

Two main objects

A JUCE plugin boils down to two classes, and Metulifer follows that model exactly:

ClassFilesRole
MetuliferAudioProcessorSource/PluginProcessor.{h,cpp}state, parameters, sequencer engine, DSP
MetuliferAudioProcessorEditorSource/PluginEditor.{h,cpp}UI, 30 Hz timer, cables, pagination

The processor owns the AudioProcessorValueTreeState (APVTS); the editor only attaches to it. That is what lets the state survive the window being closed.

Source tree

Audio flow

processBlock() is the real-time heart. It performs no allocation and never touches the ValueTree: everything it needs is read from std::atomic values.

The key step is 6: events carry a precise sample offset, so the block is split and notes fire exactly on time — no jitter tied to the buffer size.

Control flow

The UI never talks to the DSP directly:

  • SliderAttachments keep a knob in sync with a parameter (both directions).
  • The audio thread reads the std::atomic<float> values exposed by the APVTS: lock-free.
  • The display and state buttons listen to parameters, so they also follow host automation.

Three serialised states

getStateInformation() writes a root MetuliferState ValueTree containing:

ChildContentType
APVTSthe 209 parametersValueTree
stepsproperties p0…p5, one 32-bit pattern per sequenceValueTree
modone cable { src, dest } child per LFO cableValueTree

Everything is converted to XML then to binary (copyXmlToBinary).

Why three trees?

Parameters are host-automatable; steps and cables must not be. Keeping them apart avoids polluting the DAW automation with 192 steps and keeps getStateInformation() readable.
